# Smoke test: hece core engine in real Claude Code

- **Date:** 2026-10-19
- **Setup:** `claude -p … --plugin-dir <repo> --model sonnet --permission-mode acceptEdits`, run in a fresh git repo, one headless turn per step. An interactive session in `/tmp/hece-smoke` confirmed that the plugin loads and the flow starts.
- **Feature:** `greet.js`: prints `Hello, <name>!`, defaults to World, `--shout` prints in capitals.

## What worked

| Step | Evidence |
|---|---|
| Skill triggers and starts a flow | `flow_set_phase discuss` was recorded. Claude asked **one** question and asked for the user's idea first (`discussion.first: me`). |
| Decisions recorded | `Discussion (2 decisions)` |
| Plan stops for approval | `Plan (2 slices) — waiting for approval` |
| Edit blocked before plan approval | `blocked · Write · greet.js · "hece: no code edits before the user approves the plan"`, and no file was created. `flow_start_slice` was also refused. Claude explicitly declined to bypass the guard through Bash. |
| Typed approval | `continue` produced `approved · plan · via typed`, then `approved · slice 1 · via typed` |
| Slice stop | Claude built slice 1, ran it, gave a short explanation with a box diagram, then stopped with `■ 1. … ← waiting for you` |
| Next slice blocked while waiting | "go ahead and do slice 2" was refused by `flow_start_slice` ("slice 1 is waiting for the user"). `greet.js` was unchanged. |
| Feature result | All 5 example invocations behaved correctly |

## Issues found (for the final review and plan 2)

1. **The skills tell the user to "approve in the Flow panel".** That panel doesn't exist until plan 2. The skills should say "type `continue`, or pick Continue" and mention the panel key only when the frame is running.
2. **The agent can set `phase: build` without an approved plan.** It did, then set it back itself. This is harmless, because guards check plan approval and not the phase, but `flow_set_phase` is fully permissive. Consider refusing `build` while the plan is unapproved and guards are on.
3. **Activity misses the start of a session.** Hooks are silent until `flow.json` exists, so the first prompt and the `prefs_get`/`flow_get` calls are never logged. This is acceptable by design; note it for the Activity panel.
4. **Picker approval was not exercised.** Headless mode has no picker. This is covered by Task 11, with the user picking `Continue` interactively.
5. **The polling status loop flickered.** This came from the test harness (`clear` every 2 s), not from hece. Plan 2's panels should watch `flow.json` and redraw only on change.
